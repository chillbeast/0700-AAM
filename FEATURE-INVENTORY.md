# Firmware functionality inventory

Snapshot: 2026-10-28; community simulator v0.1.2, based on the v0.1.1 audit commit e5f5ea8c plus O1-O6 playback/DSP and live-preview repairs, the vector panel and its saved layout toggle. The v0.1.1 release predates those additions. See RELEASE-NOTES.md for the release scope and checks.

**v0.1.3 platform update:** Linux x86_64 joins Windows x64 with the same panel/UI/engine. Portable runtime paths and explicit desktop device guards are community extensions; they do not change the 165 base-firmware capability classifications below. Desktop builds disable embedded CV/I2C, USB gadget, network configuration, firmware flashing and host power commands. System audio/MIDI remain available; device acceptance rows still require physical hardware. See [release checks](RELEASE-NOTES.md) and [Linux setup](Kick/how-to/release-simulator.md#linux-desktop).

This is an inventory of user-facing capabilities in the checked-out firmware, its manual, panel protocol and registered screens. It records implementation evidence, stored state and the next acceptance check. It is not a certification of every hardware path, effect algorithm or combination of settings.

Present means a source implementation/path exists. Partial means a known missing or miswired part remains. Missing means a named operation has no effective implementation on the inspected path. Unverified means its implementation or supplied content cannot be established by this inventory. None of these labels alone means complete end-to-end acceptance.

Verification: R = related portable regression coverage (often engine/data only, not every UI control); S = source inspection; D = physical-device/Linux acceptance required; U = unresolved; Probe = a separate targeted reproduction. State describes where the feature should live, not a claim that its round trip has been tested.

## Summary

The reviewed matrix has **165 capability groups**: **104 present**, **27 partial**, **31 missing**, **3 unverified**. These are capability groups, not a completion percentage; the community extensions are listed separately at the end.

The structural indexes account for all **54 button-command IDs** (including bank commands and the virtual Color Edit ID), **34 screen IDs**, and **29 KickHome screen registrations**. A heuristic index records **1,079 callback/signal/event-method candidates** in C++ source and headers under kick_ui, program_edit_ui, kick_ui_settings and kick_ui_channel_mixer. Those candidates include internal notifications and optional lifecycle hooks; their count is not a feature count.

- [Capability spreadsheet](docs/audit/feature-capabilities.csv): this matrix in CSV form.
- [Panel command index](docs/audit/panel-command-index.csv): every command ID and its live source references.
- [Screen index](docs/audit/screen-index.csv): every enum ID, component and registration status.
- [Control/event index](docs/audit/feature-controls.csv): source location, excerpt and excerpt hash for callback and event-handler candidates.

The scan is a navigation aid, not a C++ semantic parser. Inherited controls, attachments, switch dispatch, virtual methods and preprocessor branches were checked manually where needed. An empty callback is not automatically a gap: recorder UI can update from its timer, and bus controls use CachedValue signals even though an older ValueTree callback is empty.

## Repair and acceptance order

The preview ownership regression (BR-05) and concurrent live audition race (BR-04) were reproduced, corrected and regression-tested before v0.1.2. The remaining priorities are:

1. **Finish visible controls that silently do nothing:** List Timing Correct, time signatures, MIDI CC editor state, audio input/arm/monitor, return/output solo, master limiter, sample Pitch Shift/Time Stretch/Bit Reduce, XY FX. Every implementation needs an observable result and failure feedback.
2. **Complete core musical workflows:** count-in/replace/swing/Note Repeat, partial step pages/triplets, Song-to-Sequence and audio bounce/export, audio-region editing/automation, sample assignment and loops.
3. **Close persistence and resource gaps:** project defaults/launch policy/autosave restore, purge, export error propagation, saved mappings and all program-type round trips.
4. **Perform device acceptance:** CV/calibration, MIDI loopback, Wi-Fi/Ethernet, updater/USB/UART, removable media, Linux recovery and ARM audio deadlines. No destructive device acceptance was attempted for this inventory.

## Panel and screen coverage

All declared command IDs are in the panel index. Global screen-open actions live in KickHome; individual screens handle transport, banks, pads and Q-links. Default TAP TEMPO/MASTER, NOTE REPEAT/LATCH, AUTOMATION, TC/ON-OFF and 16 LEVELS lack their advertised performance actions. MIDI Learn references or simulator buttons are not evidence that those actions exist.

The five Screen IDs without a KickHome registration are Invalid (sentinel), HomePreferences and EditProgram (reserved/legacy), SystemResources (separately hosted UI) and Temp (disabled demo). They are not counted as five missing product screens. The seven Program Edit components are hosted beneath the registered MenuProgramEdit screen.

## Reconciliation with the older manual and audit

- Sampler Clear/Export now have implementations. Song Export now produces MIDI, while rendered audio export and Convert to Sequence remain absent.
- External MIDI clock selection and sustain were added in the audit repair pass. Mono Modular effects, exact coefficient caching, source lifetime fixes and synchronized live audition are included in v0.1.2.
- Autosave is not a blanket stub: KickXML contains shared enable/interval state, a dirty-tree timer and a save path. Restart/configuration acceptance remains open, and most new-project defaults still lack complete creation consumers.
- MIDI CC output exists in the engine. The editor gap is its unassigned state binding, not the absence of a CC sender.
- Filter DSP exists and is tested; that does not establish a complete exposed drum filter UI. Likewise storing Warp or automation properties does not prove every playback consumer.
- Half/Double Sequence Length uses a float multiplier overload; the apparent float-to-int suspicion is rejected.
- Empty constructors and optional lifecycle handlers are not treated as missing features. Four empty insert slots are intentional and do not mean removed effects return.
